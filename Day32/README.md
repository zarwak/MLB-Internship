# Day 32 - Smart Parking Occupancy Detection

Day30 introduced tracking (`model.track(..., persist=True)`), Day31 built
line-crossing counting on top of it. Day32 uses the same
YOLOv8n + ByteTrack stack for a different question: not "how many vehicles
crossed a line" but **"which of these specific, fixed parking spaces has a
vehicle in it right now."** That's a spatial-overlap problem, not a
crossing problem, and it needed a new idea - a parking space is a *region*,
not a line, and it has to be defined before any detection can be checked
against it.

The project shipped twice. The first pass covered 2 ground-level videos
with plain COCO-pretrained YOLOv8n and documented a real limitation: a
steep top-down camera angle defeats a detector trained on ground-level
traffic photos (see "Real challenges faced"). The second pass fixed that
by fine-tuning a second YOLOv8n checkpoint on an aerial car dataset and
added 2 aerial sample videos - `parking_detection.py` and `app.py` now
pick whichever of the two checkpoints matches the footage automatically.

## How parking spaces are defined

A parking space is a **4-point polygon**, stored as *fractions* of frame
width/height (0-1) - the same resolution-independent convention Day31 used
for its counting line and ROI, so a layout calibrated once still lines up
correctly no matter what resolution the video is decoded or resized at
(`ParkingSpace.polygon`, `parking_detection.py`).

Spaces are (almost) never drawn one at a time. `generate_grid_layout()`
takes a **trapezoid** - a top (far) edge and a bottom (near) edge, each an
x-range, plus the two y-positions - and subdivides it into a rows x cols
grid of quadrilateral cells via bilinear interpolation (the same technique
used to UV-map a flat grid onto a perspective-distorted quad). A trapezoid
rather than 4 free-floating points, because that's the natural shape of an
elevated/oblique camera looking down a row of spaces: the near row is
wide, the far row is narrower. That collapses the UI to **two range
sliders + two y-sliders + rows/cols** instead of dragging 8 independent
points around - `app.py`'s sidebar, with a live preview image (the grid
drawn over the video's first frame) that updates as the sliders move, no
processing required.

For all 4 shipped sample videos, a matching `<name>_spaces.json` sits next
to each clip in `sample_videos/` - generated by feeding trapezoid
parameters into `generate_grid_layout()`, then serialized with
`save_layout()`. The app auto-loads that preset when you pick a sample
video; for an upload, or to override a sample's preset, the sidebar's
manual sliders take over - same function, same data shape, just
user-supplied numbers instead of committed ones. The 2 ground-level
layouts were hand-picked by eye against an extracted first frame, then
verified against real detections. The 2 aerial layouts went further after
an eyeballed first pass proved too coarse (see "Real challenges faced"):
their trapezoid parameters - band boundaries and column count - were
derived directly from the median size and spacing of the detector's own
real detections across several frames, not eyeballed at all. Both
`_spaces_v1_oversized.json` files are kept alongside the shipped ones as a
record of what "looked reasonable" but measured badly.

One honest limitation this surfaced: a generated grid can only be as
"real" as the lot it's drawn over. `courtyard_lot` has actual painted line
markings, so the grid's cell boundaries can be (and are) calibrated to
trace them - what you see is what's really painted on the ground.
`mall_curbside_lot` is a plain curbside row with **no** painted individual
stalls at all - there's nothing for the grid to trace, so its 8 "spaces"
are a reasonable but ultimately synthetic subdivision of the curb into
car-sized cells, not a match to any ground truth. The occupancy math is
identical either way and both are legitimate real-world cases (unmarked
curbside parking exists), but if you want to visually sanity-check a grid
against the video yourself, `courtyard_lot` is the one to use.

**`slot_annotator.py`** is a third option for a new camera angle, for when
neither a generated trapezoid nor manually recomputing one from measured
detections (the aerial recalibration above) is worth the effort: open a
video's first frame in an OpenCV window, click-drag-release a box over
every real parking space by eye, `s` to save. It writes the exact same
`ParkingSpace` JSON format as `save_layout()`, so the result is a normal
layout file the app or batch script can load like any other - only needed
once per camera angle. It's a local, GUI-driven tool, not part of the
deployed Streamlit app, so it needs a non-headless OpenCV build even though
`requirements.txt` intentionally pins `opencv-python-headless` for the app
itself - see the script's own docstring for the one-line workaround.


## How vehicle detection works

Two checkpoints, chosen automatically by which sample video is picked
(`app.py`'s `use_aerial_model`, `coding_practice/02_batch_all_videos.py`'s
`model_for()`):

- **`yolov8n.pt`** - plain COCO-pretrained YOLOv8n, restricted to
  **car / motorcycle / bus / truck** (COCO class ids 2, 3, 5, 7) - identical
  model and class set to Day30/31, no custom training. Used for
  `courtyard_lot` and `mall_curbside_lot` (ground-level/elevated-window
  cameras).
- **`vehicle_detection_aerial.pt`** - the same YOLOv8n architecture,
  fine-tuned on [CARPK](https://universe.roboflow.com/elpida-eleftheriadi/carpk-xk8e1/dataset/1)
  (1,567 aerial parking-lot images, single class `car`) via
  `train_aerial_yolo_colab.ipynb` on a free Colab T4. Used for
  `aerial_diagonal_lot` and `aerial_numbered_lot` (steep top-down drone
  cameras) - see "Real challenges faced" for why plain COCO YOLOv8n cannot
  be used here at all (it was measured to find ~0 vehicles at this angle),
  and check the Roboflow Universe page linked above for CARPK's current
  license terms before any commercial use.

Either way, detection and tracking happen in the same call:
`model.track(frame, persist=True, tracker="bytetrack.yaml", ...)`, one
frame at a time, with `persist=True` keeping ByteTrack's internal state
(and therefore every vehicle's ID) alive across frames for the whole clip -
see Day30's README for the full explanation of why that flag is
load-bearing.


## How occupied/free status is calculated

Bounding-box **containment** ("is the box inside the space") was the
obvious first idea and the wrong one - it fails the moment a car is cut off
by the frame edge or partly hidden behind its neighbor, which is exactly
the "partially visible vehicle" case the brief calls out. Instead, every
space/vehicle pair is tested by **area overlap ratio**:

1. Convert both the space polygon and the vehicle's box to pixel
   coordinates for the current frame, and sort each one's 4 points into a
   consistent rotational order (`_order_ccw`) - `cv2.intersectConvexConvex`
   requires simple, correctly-wound convex contours.
2. `cv2.intersectConvexConvex(space_poly, vehicle_poly)` computes the
   **exact** intersection area via polygon clipping (not a bounding-box
   approximation), for **every** vehicle/space pair in the frame - the full
   overlap matrix, not just each space's independent best match.
3. **One-to-one assignment, not independent per-space matching.**
   `scipy.optimize.linear_sum_assignment` (the Hungarian algorithm) finds
   the vehicle<->space pairing that maximizes total overlap across the
   whole frame, so one vehicle can claim at most one space and one space at
   most one vehicle. Checking each space independently against "whichever
   vehicle overlaps it best" - the original approach - let a single car
   straddling two adjacent cells register as two occupied spaces at once;
   measured to happen in **every frame** of `aerial_diagonal_lot` before
   this fix (see "Real challenges faced"). Only pairs the algorithm
   actually assigns (overlap > 0) count; a forced zero-overlap pairing,
   which happens whenever there are more vehicles than spaces or vice
   versa, doesn't.
4. `ratio = assigned_overlap / space_area`. If `ratio >= overlap_threshold`
   (default 15%, slider-tunable), that's a "hit" for this space this frame.

A vehicle only has to cover 15% of a space's area to register - so a car
sticking halfway out of frame, or two-thirds hidden behind the car in the
next spot, still counts. That's the direct fix for "partially visible
vehicles." The aerial videos' layouts were originally hand-drawn as coarse
zones (each covering several real stalls at once), which capped real
hits at 6-18% overlap and forced an unstably low 5% default just to
register anything at all - see "Real challenges faced" for the
recalibration that fixed the root cause (oversized zones, not the
threshold) and let the aerial default move to a normal, stable **15%**,
same as the general-purpose default.

**Debouncing.** A single missed detection (motion blur, a momentary
confidence dip) would otherwise flicker a space between occupied/free every
other frame. `ParkingLotState` keeps a 5-frame rolling window of hit/miss
per space; a space only flips to occupied once **>=60%** of that window
hit, and only flips back to free once **<=40%** hit - anything in between
just keeps the previous state. This is the same "state object advanced one
frame at a time" shape as Day31's `CountState`, just with hysteresis added
because occupancy is a *level* (true/false, held over time) rather than an
*event* (a crossing, counted once).


## How duplicate vehicle detection is handled

Three different things could be called "duplicate" here, and each is
handled by a different mechanism:

- **The same physical vehicle detected twice in one frame** (two
  overlapping boxes on one car) - handled by YOLO's own NMS, tuned by the
  IoU slider, exactly as in Day30/31.
- **The same physical vehicle counted repeatedly across frames.**
  `unique_vehicles_seen` is `len(state.seen_track_ids)` - a *set* of track
  IDs accumulated across the whole clip, not a running per-frame detection
  count. A car parked for all 300 frames of `mall_curbside_lot` is **one**
  entry in that set, not 300 - the same ID-based dedup principle Day30
  introduced and Day31 relied on for its counts. A track ID is only added
  to that set once it actually registers a hit against a monitored space -
  not just for appearing anywhere in frame. That distinction didn't matter
  for the first 2 videos (the frame *is* the monitored row), but it was a
  real bug for `aerial_numbered_lot`: its camera covers a ~300-car lot
  while only 10 spaces are monitored, so counting every vehicle YOLO saw
  anywhere in frame inflated `unique_vehicles_seen` to **440** across 250
  frames for a 10-space lot - almost entirely churn from cars nowhere near
  a monitored space. Scoping the count to actual hits brought it down to a
  plausible ~30 - see "Real challenges faced".
- **One vehicle marking more than one space occupied.** This is
  deliberately **not** suppressed. A car parked across the painted line
  between two spaces legitimately occupies both, and the overlap-ratio test
  evaluates each space independently - there's no rule capping "one vehicle,
  one space," because in the real world that's not always true. What *is*
  guaranteed is that a single vehicle can't inflate the *occupied count*
  twice for the *same* space - occupancy is a boolean per space, not an
  incrementing counter, so re-detecting the same car in the same spot next
  frame doesn't do anything further.


## How occupancy percentage is calculated

`occupancy % = 100 * occupied_spaces / total_spaces`, recomputed every
frame from the current debounced state (`ParkingFrameSample.occupancy_pct`,
`parking_detection.py`). The app shows the **final frame's** value as the
headline metric, and the full per-frame series as a chart
("Occupancy Over Time" tab in Monitor, the in-frame sparkline + a
`st.line_chart` in Analytics) via `analytics.py`'s `OccupancyHistory`.

**Utilization level** is a simple threshold on that same percentage
(`analytics.py::utilization_level`): **Low** <=40%, **High** >=75%,
**Medium** in between. Round numbers, not fit to any dataset - they're a
communication device (should a driver expect to find a space quickly?),
not a measurement.


## Difference between the two demo variants

Both variants run the **exact same** detection/tracking/occupancy pipeline
(`parking_detection.process_video()`) - they produce identical occupied/
free/occupancy numbers for a given video (see the Results table: every row
in `outputs/occupancy_results.md` has matching numbers between its
`monitor` and `analytics` entries). The difference is entirely in
*rendering*, and it's deliberately not just a palette swap:

- **Parking Monitor** (`parking_detection.py::render_monitor_frame`) - a
  full-frame operational overlay. Every space is filled translucent
  green/red, every tracked vehicle gets a full box + `#id class conf`
  label, a top-left badge shows live total/occupied/free counts. Busy,
  "watch the whole lot" look.
- **Parking Analytics** (`analytics.py::draw_analytics_frame`) - spaces
  shrink to a thin outline + a small centroid dot, vehicle boxes disappear
  entirely, and the canvas gets **physically wider**: a solid docked panel
  is appended to the right of the video (not overlaid on top of it) with a
  big occupancy %, a colored utilization bar, occupied/free/total counts,
  a trend sparkline, and a frame/timestamp footer. Dashboard-first look.

That "docked panel that widens the canvas" choice - rather than a
translucent overlay on the existing frame - is what makes the two outputs
look like different *applications*, not the same screenshot in different
colors. (It also meant catching one real bug: the panel width has to keep
the total canvas width even, or `libx264`/`yuv420p` refuses to encode the
result - see `analytics.py::draw_analytics_frame`.)


## Real challenges faced (measured, not guessed)

**Finding a genuinely static camera was the hardest part of this project -
harder than any of the detection/geometry code.** 40+ candidate "parking
lot" stock videos were downloaded and measured (ORB feature matching
between frame 0 and later frames, converted to % frame-shift and a scale
factor) across two shipping passes before landing on the 4 that shipped.
This section is written in the order the problems were actually found,
including several mistakes that made it into an earlier version of this
repo and were caught by directly reviewing the running app or re-measuring
rather than trusting the numbers alone:

- **Cinematic drone establishing shots look static in a single frame and
  are not.** The great majority of candidates (Pexels, searched as
  "parking lot" / "parking lot cctv" / "shopping mall parking lot") passed
  an eyeball check on their opening frame, then measured **9-40%
  frame-to-frame drift by the 2-4 second mark** - continuous pans, pushes,
  or zooms, the standard vocabulary of drone b-roll. One clip had already
  zoomed to 1.23x scale by frame 30 - one second in; another panned enough
  that its whole subject left frame by frame 120. A slow drone push-in
  over a well-marked shopping-center lot was tested extensively (it
  detects vehicles very well - 40+ per frame) and even briefly shipped,
  because occupancy tracking is provably tolerant of a *pure* zoom (it's
  radially symmetric, so a space near the frame's own center barely moves
  even as scale changes - unlike a *pan*, which translates everything
  uniformly off a fixed polygon). But **"fixed camera" turned out to be a
  hard requirement, not a soft preference** - tolerating motion isn't the
  same as not having it - so that clip was cut entirely rather than kept
  as a caveated exception. Every video in this repo now measures under
  0.3% frame-to-frame drift for its **entire** runtime, not just an
  opening window.
- **A steep-but-not-quite-nadir camera angle can be just as fatal to a
  COCO-pretrained detector as the fully-overhead angle Day31 documented -
  and it's exactly the angle that produces the clearest-looking painted
  lines.** Several candidates with a real, measurable elevation angle (not
  literally straight down) were visually excellent - clean marked rows,
  obvious vacant spaces, good lighting - and detected almost nothing: one
  returned **1 detection total** across a whole clip; another found only
  7-28 of 80+ visibly parked cars; a third (perfectly static, and the
  clearest single lot found in the entire search - individually numbered
  spaces painted on the ground) returned **zero** vehicle detections at
  every confidence threshold down to 0.05. This is the central tension of
  the whole search: the steeper/higher the angle, the more legible the
  markings, and the less a ground-level-trained detector can recognize a
  car from directly above it. Every steep-angle candidate was dropped.
- **A calibrated grid can look right in a screenshot and still be wrong -
  verify against real detections, not just against your own eyes.**
  `courtyard_lot`'s space layout was originally calibrated by eye against
  an extracted frame and looked correctly placed on review. It shipped
  that way. Testing prompted by direct feedback on the running app
  (occupied spaces reading far lower than the video visibly showed) traced
  the actual cause: the calibrated trapezoid sat measurably **below** the
  real car row - overlapping mostly grass and empty pavement in the
  foreground, clipping only the bottom edge of a couple of vehicles - a
  vertical offset invisible at a glance but fatal to overlap-ratio math
  (most spaces measured 0% overlap against real, correctly-detected cars
  sitting just above the polygon). Fixed by re-cropping and re-measuring
  the actual car-row pixel band directly, then re-verifying with an
  overlay of the **live detection boxes on top of the space polygons**
  (not just the polygons on top of a static frame) before accepting the
  calibration. That overlay check - detections vs. polygons, not eyes vs.
  a screenshot - is now the actual verification step, and it's what
  should be trusted over a "looks fine" visual pass.
- **A clip that ends at 100% occupied (or 0%) is a poor demo, even when
  it's a correct result.** A full-length version of the since-dropped
  drone push-in clip technically tracked occupancy correctly the whole
  way, but the push-in fills the entire row by the end, so the
  "final frame" metrics the app headlines read 9 occupied / 0 free -
  correct, but it never demonstrated the system recognizing a genuinely
  **empty** space, which is half of what "occupancy detection" means.
  The general lesson carried forward: a demo clip's *ending* state matters
  as much as its correctness, and both shipped videos were checked to
  confirm they end on a real, stable occupied/vacant mix, not an extreme.
- **A camera-distance effect on detection confidence, not a bug, explains
  `courtyard_lot`'s low occupancy number.** At the app's default confidence
  (0.15 - already lowered from Day30/31's 0.25, see below), YOLOv8n finds
  only 2-7 of the ~15 visibly parked cars in `courtyard_lot`'s frame
  (measured directly: 20 detections at conf=0.05, 10 at conf=0.1, 2 at
  conf=0.25 - Day30/31's default). `mall_curbside_lot` (closer to camera)
  detects reliably at 0.25. The fix that's actually in the shipped code:
  **`DEFAULT_CONF` was lowered project-wide to 0.15** (from Day30/31's
  0.25) once this pattern showed up, and the app's confidence slider lets
  it go lower still per-video. This is a genuine "farther from camera =
  lower confidence" detector behavior, not a threshold picked to make a
  number look better - dial the slider down to ~0.08-0.10 on
  `courtyard_lot` in the app to see a fuller (still not complete) picture.
  Raising the processing resolution (skipping the 960px downscale) was
  also tested and helped only marginally - the limit is genuinely how
  small the cars are in the source frame, not a fixable pipeline setting.
- **CPU-only inference cost is per-frame, not per-second** - same finding
  as Day31. `mall_curbside_lot` (300 frames, the app's own processing cap)
  takes ~42s; `courtyard_lot` (216 frames) takes ~30s. Roughly linear in
  frame count regardless of clip duration or resolution differences
  between sources.
- **The steep-angle limitation above is a detector problem, not a physics
  problem - fine-tuning fixes it.** `vehicle_detection_aerial.pt`
  (YOLOv8n fine-tuned on 1,567 CARPK aerial images, see "How vehicle
  detection works") turns the exact failure mode documented above into a
  working detector: on `aerial_numbered_lot` - the same style of steep,
  clearly-marked top-down lot that returned **zero** detections at every
  confidence threshold down to 0.05 with plain COCO YOLOv8n - the aerial
  checkpoint finds **300 vehicles in a single frame** at conf=0.15,
  confidences mostly 0.75-0.87. The tradeoff: it's aerial-only, and was
  never tested against ground-level footage - `app.py` and the batch
  script pick the checkpoint by video, they don't try to auto-detect
  camera angle.
- **A ROI that's a small slice of a busy scene breaks an assumption the
  first version's "unique vehicles" count made silently.** Wiring up
  `aerial_numbered_lot` (10 monitored spaces inside a ~300-car lot) surfaced
  a real bug: `seen_track_ids` counted every vehicle YOLO tracked anywhere
  in frame, not just ones near a monitored space - harmless when the frame
  *is* the monitored row (the first 2 videos), but it inflated
  `unique_vehicles_seen` to **440** across 250 frames for a 10-space lot,
  almost entirely ID churn from the ~290 other cars nowhere near a
  monitored space. Fixed by only counting a track ID once it actually
  registers a hit against a monitored space - see "How duplicate vehicle
  detection is handled".
- **A second "cinematic drone push-in," caught the same way the first one
  was.** `aerial_mall_lot.mp4` was downloaded, given a hand-calibrated
  layout, wired into the app, and produced plausible-looking numbers
  (7/8 occupied) - all before its camera motion was actually measured.
  RANSAC-filtered frame-to-frame drift came back at 0.56-0.98%, several
  times every other shipped video's <0.3%, and frame 0 vs. frame 249 shows
  why: the mall entrance sign grows from small and distant to filling most
  of the frame - a continuous zoom, the identical failure mode the first
  pass of this project already found and rejected once (see the "cinematic
  drone establishing shots" finding above). Consistent with that earlier
  call - "fixed camera" is a hard requirement, not a soft preference - the
  clip was pulled from the shipped set rather than kept with a caveat; it's
  parked, unused, in `sample_videos/dropped/`. The lesson repeats because
  it's easy to forget under time pressure: a layout and occupancy numbers
  that look right on screen are not a substitute for actually measuring
  camera motion before a video ships.
- **Both aerial layouts' "spaces" were actually multi-stall zones, not
  individual stalls - and the fragile 5% overlap default was a symptom of
  that, not the real problem.** `aerial_diagonal_lot`'s 12 zones and
  `aerial_numbered_lot`'s 10 zones were each hand-drawn to cover a whole
  cluster of real parking stalls (visually confirmed: one zone contained
  3-5 real cars). A single detected car could then only ever cover a small
  slice of its zone's area - measured 6-18% overlap for genuine hits, which
  is *why* the threshold had to sit at a fragile 5%: anything higher
  (even 0.15) collapsed **both videos to 0% occupied**, and
  `aerial_numbered_lot`'s 100% figure was really "at least one car touched
  this oversized zone somewhere," not "this specific stall is full."
  Fixed by measuring real car footprints directly from the detector's own
  output (median ~0.02x0.03 of frame size), confirming each zone actually
  spanned 2 real sub-rows of stalls stacked inside it, then rebuilding both
  layouts as fine grids sized to that measurement -
  `aerial_diagonal_lot` went from 12 zones to a 64-space grid,
  `aerial_numbered_lot` from 10 to 52. Real-hit overlap ratios rose to a
  median of 29% (up to 71%), occupancy now degrades *smoothly* as the
  threshold rises instead of falling off a cliff, and the default moved to
  a normal, stable 15%. The general lesson: a threshold that only works at
  one fragile value is usually compensating for a geometry problem
  upstream, not evidence that the threshold itself needs more tuning.
- **A single vehicle could independently register as "occupying" more than
  one space at once - found by comparing this project's approach against a
  different intern's independent implementation of the same brief.** Their
  writeup called out one-to-one Hungarian-algorithm matching as the fix for
  exactly this failure mode, which prompted checking whether this project's
  own "test every space against whichever vehicle overlaps it best,
  independently per space" logic had the same gap. It did, measurably: a
  frame-by-frame check found **every single frame (375/375)** of
  `aerial_diagonal_lot` had at least one vehicle claimed as the best match
  by 2 or 3 adjacent spaces simultaneously - one real car straddling two
  now-tightly-packed cells (a side effect of the recalibration above:
  smaller, more accurately-sized cells put real vehicles closer to cell
  boundaries) was being counted as two or three occupied spaces. Fixed with
  `scipy.optimize.linear_sum_assignment` (Hungarian algorithm) on the full
  vehicle x space overlap matrix, constraining each vehicle to at most one
  space and vice versa - see "How occupied/free status is calculated".
  Confirmed fixed (0/375 frames with a double-claim after) and confirmed to
  matter beyond the two recalibrated aerial layouts: `mall_curbside_lot`'s
  occupied count (untouched by the recalibration) also dropped, from 5/8 to
  4/8, once one vehicle could no longer double-claim two spaces there too.
  The external Kaggle validation below shows the size of the effect most
  clearly: precision jumped from 90.4% to 99.8%. The general lesson: a
  second, independent implementation of the same spec is worth reading even
  after your own version already works and is already validated - "works
  and is validated" only covers the failure modes your own validation
  happened to exercise.


## External validation against independent ground truth

Every number above comes from this project's own videos and layouts - a
real but limited check, since the same person who drew the space polygons
also judged whether the results "looked right." To get a check that isn't
circular, the occupancy pipeline was run against the
[Kaggle "Parking Space Detection & Classification" dataset](https://www.kaggle.com/datasets/trainingdatapro/parking-space-detection-dataset)
(CC BY-NC-ND 4.0 - not redistributed here, see below) - 30 drone top-down
photos with 903 independently hand-labeled parking spaces (free / occupied
/ partially free), built by a different team for a different purpose.
`coding_practice/03_validate_kaggle_dataset.py` reuses
`parking_detection.py`'s own `_order_ccw` + `cv2.intersectConvexConvex` +
Hungarian one-to-one assignment code directly against each labeled polygon
(no video, no debounce - a still-image hit is just `assigned overlap >=
threshold`), so this measures the actual shipped occupancy logic, not a
reimplementation of it.

Results, in the order they were found:

- **Plain `yolov8n.pt` confirms the known limitation, on a dataset it had
  never seen.** All 30 images are true nadir drone shots. Detection counts
  per image were often far below the labeled space count (one image: 18
  occupied spaces labeled, 6 vehicles detected total; another: 12 labeled,
  **0** detected) - the same "steep angle defeats a COCO-pretrained
  detector" finding as `aerial_numbered_lot`, independently reproduced.
  Accuracy across every overlap threshold from 0.02-0.60 stayed at
  49-54% - barely better than chance, and not fixable by retuning the
  threshold, because most occupied spaces had **no detection to threshold
  against at all**.
- **`vehicle_detection_aerial.pt` generalizes: 80-86% accuracy on images it
  was never tuned against.** At `overlap_threshold=0.05` (this project's
  default at the time): 81.7% accuracy, 90.4% precision, 82.5% recall
  (n=897 spaces, excluding the 6 ambiguous "partially free" ones). Sweeping
  the threshold found the accuracy/F1 peak at **0.30** (85.8% accuracy,
  F1=0.888) - a real, useful signal.
- **Adding one-to-one vehicle<->space assignment (below) turned that into
  86.4% accuracy, 99.8% precision, and - notably - an accuracy curve that's
  now flat across nearly the whole 0.02-0.30 threshold range instead of
  peaking narrowly at 0.30.** Independently checking each labeled space
  against "whichever vehicle overlaps it best" let one real vehicle
  register as a hit for more than one labeled space whenever the labels
  were densely packed, inflating false positives - that's exactly what
  capped precision at 90.4%. Constraining each vehicle to at most one space
  (`scipy.optimize.linear_sum_assignment` maximizing total overlap across
  the whole image) removes those spurious extra hits: at threshold 0.15,
  502 TP / 1 FP / 122 FN / 272 TN (was measurably worse before). The
  flat accuracy curve is the more interesting result - it means the fix
  makes the whole system far less sensitive to the exact threshold chosen,
  not just more accurate at one value.
- **That mismatch was a symptom, not a dead end - it's what led to finding
  and fixing the oversized-zone bug documented below.** Re-running the
  Kaggle-suggested 0.15-0.30 range against `aerial_diagonal_lot` /
  `aerial_numbered_lot` themselves, at the time, collapsed **both to 0%
  occupied** - a huge red flag, since every space's real overlap topped
  out around 6-18% against those clips' own layouts. Chasing *why* (not
  just accepting "different datasets need different thresholds" and moving
  on) led directly to discovering that this project's own aerial layouts
  were drawn as coarse zones spanning several real stalls each - see "Real
  challenges faced". After recalibrating both layouts to real per-stall
  size, `DEFAULT_AERIAL_OVERLAP` moved to a normal, stable **0.15** - much
  closer to the Kaggle-validated optimum, and no longer a razor's-edge
  value one bad frame away from breaking.

**On the dataset itself:** it's a small free "teaser" sample from a
commercial data-labeling vendor (CC BY-NC-ND 4.0 - non-commercial,
no-derivatives), not something this repo re-hosts or ships. Only the
aggregate numbers above are recorded here;
`coding_practice/03_validate_kaggle_dataset.py` needs your own local copy
(`kaggle datasets download -d trainingdatapro/parking-space-detection-dataset`,
unzipped next to the script) to re-run it.

## The Streamlit app - Smart Parking Occupancy Detection

`app.py` - pick **Parking Monitor** or **Parking Analytics** in the
sidebar, pick a sample video (auto-loads its preset space layout and
switches to the aerial detector automatically for the 2 aerial samples) or
upload your own (define a layout with the trapezoid+grid sliders, with a
live preview, and a checkbox to switch on the aerial detector for
drone/top-down footage), tune confidence/IoU/occupancy-overlap thresholds,
run, and get back: the annotated video, 5 summary metrics, a utilization
badge, a per-space status table, an occupancy-over-time chart, and a
download button.

Run locally: `streamlit run app.py` (see `HOW_TO_RUN.txt`).
